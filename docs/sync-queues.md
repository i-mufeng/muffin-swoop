# 周期同步队列

D05 的实现范围是重新检查队列中已完成的下载，发现远端更新时安全替换该任务拥有的文件。它不镜像整个目录，也不删除远端已消失的本地文件。

## 配置与接口

队列窗口提供「同步已完成文件」开关和「立即同步」按钮。开关默认关闭，和队列计划一起持久化。

- `QueueSnapshot.sync_enabled`：当前持久化开关。
- `Engine::set_queue_sync_enabled(queue, enabled)`：更新开关；仅打开开关不立即下载。
- `Engine::sync_queue(queue) -> Result<usize>`：启动队列并安排一次检查，返回新排队的检查数量，不改变持久化开关。
- `Engine::start_queue(queue)`：启用同步的队列会同时安排已完成成员检查。
- `QueueSchedule`：每次消费开始边界时安排检查，包括队列已处于运行状态的重复开始边界。错过的历史周期不会逐个补跑。

同步和普通下载使用相同的队列槽位与顺序，并遵守队列并发、任务限速、全局限速和共享流量配额。停止队列会取消在途检查或下载，保留等待状态；下一次启动可继续。

单独暂停的任务不会被周期开始或「立即同步」恢复，必须显式继续该任务。失败的同步任务可显式继续，也可在下一周期重试。所有同步重试都使用新的临时文件，不续接旧的暂存内容。

## 文件归属与远端检查

新下载完成后记录目标的规范路径、SHA-256、大小、请求身份摘要和已验证的远端 ETag / Last-Modified。任务地址或请求头变化后，不沿用旧请求身份的“未变化”结论。

旧版数据库中的完成任务没有归属指纹。它们不会通过扫描现有文件自动补凭据；首次同步会失败并说明原因。需要另建下载任务完成一次下载，才有可同步的归属记录。普通下载已续传的片段如果缺少足够的响应验证记录，第一次同步也会保守地完整获取。

每次同步先检查本地文件。目标必须是普通文件，规范路径、大小、SHA-256 必须与完成记录匹配；符号链接、文件丢失、路径改变或用户编辑会停止同步并保留现状。

远端采用探测比较：

- 相同强 ETag 且大小相同，跳过正文下载。
- 无可用强 ETag 时，可用相同 Last-Modified 和大小判定未变化；已变化的 ETag 不会被相同时间戳掩盖。
- 缺少可比较的验证器时，必须完整获取后比较 SHA-256。字节相同则保留现有文件、完成时间，不重复触发完成动作。

HTTP 同步正文使用一个完整 GET。强 ETag 会附带 `If-Match`，响应验证器变化或缺失、远端大小变化、短读、过量内容等均拒绝发布。完整响应读至 EOF，再校验暂存文件长度和 SHA-256；普通下载仍保持现有多连接模式。

FTP/FTPS 不使用 SIZE/MDTM 快捷判断未变化，始终完整暂存并比较内容。FTP 最终响应成功后才进入发布流程。

## 临时下载与发布

正文先写入目标同目录下随机创建的 `.swoop-sync-*` 临时文件，原文件继续可用。写入流量照常计入配额，失败重试的实际写入也计费；探测与网络栈预取不属于该字节账本。

下载完整成功后再次校验原文件，发布前还检查目标和暂存文件的类型、规范路径及元数据是否变化。随后把实际原文件移入同目录唯一 `.swoop-recovery-*`，校验被移动的真实内容，再用不覆盖方式发布新文件。这样外部程序在最后校验后保存的新版本也不会被无条件替换。整个过程不是跨文件原子事务，移动和发布间目标可能短暂不可用。

取消、网络错误、校验失败或发布失败时保留旧文件，移动过的文件以不覆盖方式恢复；目标已被外部新文件占用时保留两份文件，并在错误中显示恢复路径。进程被强制终止时可能遗留随机临时文件；未经验证的下载临时文件不会直接发布。原件恢复文件有持久化路径和指纹，按下节流程处理。

## SQLite 与发布边界

SQLite 与文件系统不能组成一个原子事务，因此任务的 `sync_state` 保存两份可恢复凭据：

1. `baseline` 是当前文件的已知归属凭据。
2. 完整暂存文件验证后，先将候选凭据保存到 `prepared`、唯一恢复路径保存到 `recovery_path`，同时保留旧 `baseline` 和 `pending=true`。
3. 只有这次写库成功，才移动原件、核验实际被移动文件并以不覆盖方式发布。恢复路径的初始占位带专用标记，不把未知零字节文件当作可删除占位。
4. 替换成功后，内存切到新 baseline，再保存最终完成状态。文件已经成功发布，后续完成状态写库失败不会触发覆盖式回滚。

失败时的可见状态：

| 情况 | 目标文件 | 任务及恢复行为 |
| --- | --- | --- |
| 发布 intent 写库失败 | 旧文件不变 | 任务失败，显示 SQLite 错误；清除数据库故障后可重试 |
| intent 已保存，发布前中断 | 旧文件不变 | 重启匹配旧 baseline，重新检查和下载 |
| 原件已移动，发布前中断 | 原件在恢复路径 | 重启不覆盖地恢复；目标已有用户新文件时保留两份并报错 |
| 文件已发布，最终完成状态写库失败 | 已验证的新文件 | 当前任务显示完成，写库失败记日志；数据库保留 prepared，重启可按候选 SHA-256 恢复 |
| 发布后、恢复前用户改动文件 | 用户文件保留 | 两份凭据均不匹配，任务失败；不会把旧文件回滚盖上去 |

恢复过程中只接受旧 baseline 或 prepared 描述的已知内容。`load(true)` 会将上次活动的检查重新排队；`load(false)` 保持暂停，用户继续后再执行恢复检查。

## 验证范围

本机自动测试使用真实本地 HTTP 服务、真实 SQLite 文件和拒绝指定更新的触发器，覆盖未变化、内容更新、Last-Modified、缺失验证器、探测/正文验证器不一致、短读、长度异常、取消、下载中用户编辑、符号链接、队列停止、共享配额、周期重试、重启、旧库迁移和发布前后数据库失败。

Windows 的代码路径尚未在 Windows 实机上验收。此处不将本机测试或依赖源码检查视为 Windows 实机证据。
